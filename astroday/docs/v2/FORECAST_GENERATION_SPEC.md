# FORECAST_GENERATION_SPEC — предварительная генерация прогнозов на период

## Конвейер
```
Подтверждённый доступ (оплата YooKassa / тест)
 → syncUsers: окно дат = [сегодня по местной дате, min(последний день доступа, сегодня+30)]
 → по строке на каждую локальную дату (astroday_v2_forecasts, status=pending; сегодня prio 0, завтра 1, далее 10+n)
 → ensureBazi: календарь Грабителя богатства на ВЕСЬ период доступа (без OpenAI)
 → воркер (планировщик, каждые 5 мин, до 150 с, 3 параллельно):
     calculating: движок /v2/forecast (натал + транзиты + события дня, 12:00 местного)
                  + /v2/lunar (лунные сутки на 12:00, Луна без курса; кэш на 35 дней по месту)
     generating:  selectTopics → 1–2 темы с фактами → OpenAI Responses API (JSON Schema)
     validating:  validateForecast (факты, планеты, цифры, мат, сферы, повторы, длина, род)
                  → renderForecast (Telegram HTML; числа/время/даты — только из расчёта)
                  → повторная проверка мата на готовом тексте и лимита 4000 символов
     ready:       сохранено; ручная выдача и рассылка берут текст отсюда
```
Код: `v2/queue.mjs`, `v2/topics.mjs`, `v2/editorial.mjs`, `v2/runtime.mjs`.

## Ключевые правила
- **Каждая дата — отдельный расчёт и отдельный текст.** Один месячный текст на 30 частей не режется. Тест: 31 строка → 31 различный `body_html`, ровно 31 запрос к OpenAI.
- **Платёжный webhook не ждёт генерации.** Выдача доступа не меняется. Выполнение заказа (`processFulfillment`) для пользователя v2 вызывает `firstResult`: синхронизирует период, отправляет сегодняшний прогноз, если он готов, а иначе ставит его первым в очередь с `notify_on_ready`.
- **Тестер:** «🖤 Я в деле» → старая проверенная привязка (`astrodayJoinOnce`, тихий режим) → `syncUsers` → строки на весь тестовый период, от сегодня до `trial_end_exclusive − 1`.
- **Длинные подписки (6/12 мес):** прогнозы — скользящее окно 31 день (настройка `ASTRODAY_V2_WINDOW_DAYS`), календарь Грабителя — на весь срок. Окно пополняется каждым тиком независимо от того, открывает ли человек бота.
- **Генерация не зависит от открытия бота.** Тик планировщика сам находит всех активных пользователей v2.
- **«Сегодня/Завтра»** берут готовую строку, OpenAI повторно не вызывается. Если строка не готова, бот говорит «готовлю», поднимает приоритет и запускает фоновую обработку именно этой строки (`processNow`); готовый текст придёт сам.
- **Непроверенный текст не отправляется никогда:** рассылка и кнопки читают только `status='ready'`.

## Отбор тем (`selectTopics`)
Балл = вес транзитной планеты × вес натальной точки × вес аспекта × (1 − орб/лимит)^1.3 × (сходящийся 1 / расходящийся 0.72) × (точный сегодня ×1.3).
Сфера определяется по натальному дому транзита (если время рождения известно), затем по дому натальной точки, затем по смыслу пары планет.
Первая тема — самая сильная. Вторая берётся, только если её балл не меньше 0,6 от первой и она про другую сферу. Порог 0.55. Если тем нет, выходит короткий спокойный день про фон Луны. Сила дня (`quiet/normal/strong`) задаёт допустимую длину.

## Перерасчёт и инвалидация
| Событие | Что происходит |
|---|---|
| Дата/время/город рождения, часовой пояс или текущий город | Меняется `chartFingerprint`. Невыданные дни с сегодняшнего → `invalidated`, создаются новые. Прошлые и уже отправленные не трогаются |
| Время рассылки | Ничего: не входит в отпечаток |
| Версия движка или лунного модуля | Невыданные будущие дни → `invalidated` → пересчёт |
| Промпт или модель | Готовые тексты **сохраняются** (без лишней оплаты). Новые дни пишутся новой версией; `prompt_version` и `model` записаны в строке. Принудительная регенерация — вручную, SQL-инвалидацией |
| Продление | Окно и календарь расширяются, готовые дни не пересоздаются |
| Окончание доступа | Новые строки не создаются. Кнопки показывают честный статус. Рассылка проверяет `accessCovers` |
| Обращение по имени | Действует на ещё не сгенерированные дни |

## Batch API (решение)
Batch для `gpt-6.2-astra` подтверждён пробой (§2 OPENAI_MODEL_AUDIT). В r1 генерация синхронная с приоритетом ближайших дат: 30 текстов на человека готовы за 1–2 тика, а стоимость и так около $0.7 на период. Batch даёт −50%, но до 24 часов задержки. Включать его стоит, когда пользователей станет сотни: для дат дальше 2 дней. Схема для этого готова (статусы, `generation_key`, `openai_response_id`), очередь позволяет отдельный батч-воркер. Пока **не реализовано** — помечено в IMPLEMENTATION_PLAN.

## Контроль расходов
Дневной лимит запросов `ASTRODAY_V2_DAILY_BUDGET` (по умолчанию 600, таблица `astroday_openai_usage`). Не более 3 попыток на текст. После неудачи — бэкофф 2/5/15/45/120/360 минут, всего до 6 попыток. Повторный тик не генерирует готовое заново (тест). Prompt caching срабатывает автоматически (`prompt_cache_key`).
